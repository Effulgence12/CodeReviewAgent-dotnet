## 1. 项目概述

本项目实现了一个 .NET 代码审查 Agent：用户可通过 Web 工作台、Console 命令行或 MCP 客户端提交 C# 代码；顶层对话 Agent 使用手写 ReAct 循环决定是否调用文件、分析、RAG 等工具，或触发多专家深度审查。系统还提供显式授权的修复与编译验证闭环。三个入口共享同一 Core，仅界面与权限默认值不同。

## 2. ReAct 循环解读

核心实现位于 `src/CodeReviewAgent.Core/Agent/ReActAgent.cs`。

1. 将用户输入加入 `ConversationMemory`，使同一会话可保留上下文；
2. 以 `autoInvoke: false` 请求 LLM，确保函数调用的循环控制权仍在项目代码中；
3. 模型未要求工具时，结束本轮并返回最终答案；
4. 模型要求工具时，项目代码逐一执行函数，把结果或异常作为 Observation 写回记忆；
5. 达到 `MaxSteps` 时停止，避免无限工具调用。

这套设计没有把 ReAct 交给高层黑盒：Semantic Kernel 负责协议适配，业务循环、上限、错误回灌与事件上报均由项目代码负责。

## 3. 关键设计决策

### 顶层动态、底层固定

对话 Agent 需要根据用户意图选择回答、查文件或全面审查，因此采用 LLM 驱动的动态规划；而全面审查固定需要风格、安全、性能三个角度，使用 `Task.WhenAll` 的固定流程更可预测、更便于解释。

### 工具与角色分离

“编译”是确定性能力，所以是工具；“安全判断”依赖上下文和 LLM 判断，所以是 Agent 角色。该区分避免了为每个工具虚构一个 Agent 的形式主义。

### 显式写入授权

Web 支持本机与共享目录。为了避免用户一句“审查一下”意外修改真实代码，外部目录默认只读；仅当用户显式开启写入权限时才注册修复工具。上传文件始终写入隔离会话目录。

### 配置分层

API Key 只应存在于 `appsettings.Local.json` 或环境变量中。这样默认配置可提交，机密不会进入仓库。

## 4. 遇到的问题与解决

| 问题 | 解决方式 |
|---|---|
| Web、MCP 与内部工具可能产生不同的目录权限边界 | 抽出 `ReviewDirectoryPolicy`，两种入口共用 `ReviewAccess` 配置。 |
| 多 Agent 同时输出会使流式文本交错 | 专家阶段关闭逐 token 流式，保留原子化的 step/action/observation 事件。 |
| 修复能力可能误改外部共享目录 | 默认不加载写工具，必须显式授权。 |
