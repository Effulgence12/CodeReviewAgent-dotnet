# 异常处理与资源管理

异常用于表达无法在当前抽象层正常处理的失败。不要用异常代替普通分支，也不要为了“看起来稳定”而隐藏真实故障。

## 捕获与传播

- 禁止空 `catch`。吞掉异常会丢失失败信号，使数据损坏和状态不一致更难定位。
- 只捕获能够处理、补偿或补充上下文的异常类型，避免无条件 `catch (Exception)`。
- 保留原始堆栈时使用 `throw;`，不要使用 `throw ex;`。
- 包装异常时把原异常作为 `InnerException`，并提供不包含秘密的业务上下文。
- 在 API、消息处理器和后台任务入口等异常边界统一转换错误、记录日志并决定是否重试。

## 日志与可观测性

- 同一个异常通常只在一个负责处理它的边界记录，避免每层重复日志。
- 日志包含操作、稳定标识和失败类型，但不得记录 API Key、密码、令牌或完整敏感载荷。
- 不要返回伪造成功结果；无法继续时应给调用方明确失败。

## IDisposable 与异步资源

- 对 `IDisposable` 使用 `using`/`using var`，对 `IAsyncDisposable` 使用 `await using`。
- 拥有资源的类型负责释放；仅借用由 DI 或调用方管理的对象时不要擅自 Dispose。
- `Stream`、数据库连接、响应消息等必须覆盖异常路径上的释放。
- Dispose 应可重复调用，并避免从终结器路径访问已经释放的托管对象。

## 重试与恢复

只对明确的瞬态错误做有界重试，并采用退避、取消和幂等设计。参数错误、认证失败和确定性编译错误不应盲目重试。
